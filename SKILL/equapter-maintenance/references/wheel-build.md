# wheel 打包与产物验证

仅在用户请求打包且 `wheel_build` 不为 `off` 时使用。执行策略见 [SKILL.md](../SKILL.md) 的“独立执行开关”。不要求先完成 Git 提交，不能为打包擅自运行 `git commit`；本步骤不包含上传、发布或给客户发送文件。

## 固定源码和版本

构建输入必须准确包含本次选定且已验证的代码，可任选符合任务的一种来源：

- **已有提交**：记录准确提交哈希，将该提交导出到独立目录。只有它确实包含待打包修复时才使用 `HEAD`，不能忽略未提交修复而打出旧代码。
- **未提交源码快照**：即使 `git_commit=off` 或仍待 review，也可以打包。以基础提交为起点，在独立副本纳入本次选定的已暂存/未暂存差异、必要的新文件和删除项；排除用户无关修改及旧构建产物。保留基础提交、完整差异和新增文件清单，并记录构建前快照校验值。若依赖用户已有改动，将其列明为构建输入，不能遗漏必要依赖或悄悄纳入无关内容。

快照需要能够重建本次构建输入，不能只记录 `git diff` 而漏掉新文件，也不能只有一个无法还原源码的哈希。验证这个具体副本与已测试代码一致。构建时不从仍在修改的工作区临时取文件；之后新增的修复不自动进入已固定快照。

读取 `equapter/version.py:get_version`：它把 `equater.cfg` 的 `version_main` 与部分机台版本串组合。不是所有机台都会自动参与版本号，`equapter.__version__` 也不一定等于 wheel 的发行版本。结合现有约定准备可区分且可追溯的版本，检查最终发行元数据。只打包未提交快照时，版本调整可在副本中完成，但必须记录在快照差异里；需要回写源码时纳入明确的改动范围，不自动提交。明确标注产物是否来自未提交源码，不冒称已有发布提交或标签。

## 准备并 review 构建方案

确认客户 Python 次版本/ABI、系统和架构，选用匹配的隔离构建环境；检查 setuptools、wheel、Cython、编译器及 OpenMP 条件。目标机台还可能依赖 `.so/.dll`、CUDA、.NET 或厂商运行库，以实际 import、库加载代码和客户环境为依据；不能假定 `requirements.txt` 足够，也不要无差别升级所有依赖。

准备具体的构建方案：源码提交或快照及差异、拟发行版本、目标环境和构建依赖、独立构建目录、准确命令、产物位置，以及源码回归结果和安装后验证方式。

- `review`：展示方案，明确等待用户批准这次构建；批准前可以完成源码快照、版本准备和源码测试，但不执行构建命令或间接触发构建。用户批准后，按同一方案构建并验证，不重复询问。等待期间不影响已授权的 Git 提交。
- `auto`：条件具备后直接构建并验证，无需用户再次 review。它不把 `git_commit=review` 升级为自动提交。

## 在独立副本构建

**当前构建具有破坏性：** `setup.py` 的主流程先 Cythonize，再删除 `equapter/` 中除白名单外的 `.py/.pyc`，同时清理 `build/`、`dist/`、`equapter.egg-info/`。`--help`、`--version` 也会进入该流程。`deploy.sh` 还会调用 `clean_repo.py`，后者执行 `git reset --hard`、`git clean -f -d`、`git pull`。不要在维护工作区运行这些命令，也不要在那里用 `pip install .` 或构建前端间接触发 `setup.py`。

以下仅是**构建动作已获准**且**所选来源为当前 HEAD**时的示例。当前 `python` 应已指向选定构建环境，必要资源应已提交或另行受控准备。`review` 模式不能整段提前执行；可以先导出源码准备方案，获准后才运行最后的构建子 shell。

```bash
set -e
release_commit=$(git rev-parse HEAD)
release_dir=$(mktemp -d /tmp/equapter-release.XXXXXX)
git archive --format=tar --output="$release_dir/source.tar" "$release_commit"
tar -xf "$release_dir/source.tar" -C "$release_dir"
(
    cd "$release_dir"
    python setup.py build_ext -j16 bdist_wheel
)
```

已有获准快照时直接使用该快照的构建副本，不重新取可能变化的 `HEAD`。`git archive` 不含未提交差异或新文件，不能用上例替代未提交源码快照流程。它也不含未跟踪的必要资源，须提前核查。并发数可按构建资源调整；不运行 `deploy.sh` 或 `clean_repo.py`。

失败时保留日志，在相同已记录输入的新副本中修正构建条件并重试，不用重置维护工作区来恢复源码。`review` 模式下源码、版本、目标环境等构建输入有实质变化时，展示更新方案再执行。

## 验证产物并汇报

- 检查 wheel 文件名、`METADATA` 和 `WHEEL` 中的版本、依赖与 Python/ABI/平台标签；核对 `equater.cfg`、目标解析器和所需动态库/资源实际入包，排除意外打入的 demo 或客户信息。`setup.py` 的显式 `package_data` 清单不代表所有资源都已覆盖，不能只凭包排除配置认定产物正确。
- 在匹配客户条件的干净环境安装这个确切的 wheel，从仓库外运行；确认目标模块来自安装位置。完成 import、故障样本和相关正常样本的解析回归。源码通过不等于 wheel 通过，环境不匹配时如实列出尚未完成的验证。
- 记录 wheel 绝对路径、发行版本、源码提交或快照标识及未提交差异、SHA-256、目标环境、修复摘要、测试结果以及升级/回滚信息。只交付经过验证且可追溯的产物；本地构建成功不表述为已发布或客户已更新。
