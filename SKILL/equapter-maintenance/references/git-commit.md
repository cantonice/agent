# Git 提交

仅在用户请求提交且 `git_commit` 不为 `off` 时使用。执行策略见 [SKILL.md](../SKILL.md) 的“独立执行开关”。本步骤不触发 wheel 构建，也不包含推送、打标签或发布。

## 准备具体提交

完成本任务代码修改及相关回归，检查当前分支、基础提交、`git diff` 和已有暂存内容。按文件或补丁块限定本任务改动，不混入用户原有修改、无关暂存项、客户资料或构建产物；不要为了提交清空用户暂存区。

如果用户同时要求打包、`wheel_build` 不为 `off` 且版本方案已明确，将需要持久保存的版本差异提前纳入这次提交的审阅范围。版本方案未定不阻塞独立的修复提交；后续版本修改若需提交，仍遵循 Git 开关。只请求提交时，不为了潜在打包强行升级版本。版本准备不代表已批准执行构建。

准备可直接审阅的材料：

- 目标分支、基础提交、准确文件及补丁范围，提供可查看的完整 diff。
- 根因、修复摘要和拟用提交信息。
- 已执行的测试及结果、尚未覆盖的范围。

## 根据开关执行

- `review`：展示上述材料，明确等待用户批准这份提交；批准前不运行 `git commit`。用户要求调整时先修改并验证，再展示更新后的差异。等待期间可继续独立、已授权的 wheel 工作。
- `auto`：完成审查与验证后直接提交，无需用户再次 review。

执行前核对当前差异仍与获准或已验证内容一致。仅暂存并提交本任务的准确范围；文件中混有用户已有改动时按补丁块处理，不能因显式列了文件名就提交整份无关修改。若提交因钩子或其他检查失败，先查明原因，不绕过检查；实质修改需遵循当前 review 规则。

完成后核对实际提交的文件和差异，记录提交哈希与提交信息，确认用户其他工作仍保留。推送按用户另行给出的授权执行，不擅自强推。没有提交时，不用旧 HEAD 冒充本次提交。
