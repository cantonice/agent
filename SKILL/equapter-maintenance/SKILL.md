# Equapter 机台解析维护

围绕“客户现象 → 原始资料 → 具体解析分支 → 根因 → 修复及回归”开展工作。Git 提交和 wheel 打包是独立可选步骤。使用英文说明，保留代码中的英文标识。代码路径相对 Equapter 仓库根目录，`references/` 路径相对本技能目录；每次以当前代码为准，不把凯马的格式和接口套用到其他机台。

## 判断任务范围

- **了解已有解析方法**：结合指定机台和资料说明入口、输入格式、调用链、配置及输出契约；只要求解释时不修改代码。
- **现场问题修复**：先复现客户反馈，再定位、修复和验证；是否提交、是否打包及如何执行分别由下述开关控制。
- **新增机台或格式支持**：先梳理样本与接口，再选择相近实现作为参考，完成接入及回归。
- **可选操作**：提交不触发打包，打包不要求先提交。推送、发布和给客户发送文件不包含在这两个开关内，按用户另外给出的授权执行。

## 独立执行开关

默认值如下，可在调用时直接写 `git_commit=auto wheel_build=review`，也可用含义明确的自然语言指定。这些是技能执行策略，无需修改解析库代码。

```yaml
git_commit: review
wheel_build: review
```

| 开关值 | 对该步骤的行为 |
| --- | --- |
| `off` | 不执行该步骤，不为它额外准备审批材料；继续其他已请求步骤。 |
| `review` | 完成准备与相关验证，展示具体改动或构建方案，等用户 review 并明确批准后再执行。 |
| `auto` | 在请求范围内自动准备、执行和验证，不再要求用户 review；缺失的必要信息或环境问题仍须如实处理。 |

- **范围与模式分开判断。** 默认值仅约束已请求的步骤，普通解释、开发或修复请求不会自动提交、打包。用户在本次调用显式指定某开关为 `review` 或 `auto`，同时表示请求该步骤；指定 `off` 表示关闭它。
- **沿用明确选择。** 优先采用用户最新明确指令，其次采用本次任务已确定的模式，再采用默认值。仅说“提交并打包”仍使用默认 `review`；“这次全自动修复、提交并打包”将两项设为 `auto`；“先给我 review”将相应步骤设为 `review`。不要把一次任务的选择推定为以后所有任务的默认值。
- **review 在动作前发生。** Git 执行前展示准确 diff、提交范围、提交信息和测试结果；wheel 构建前展示固定源码、版本、目标环境、构建命令及产物位置。准备工作不能提前执行待批准的提交或构建。
- **批准绑定具体步骤与内容。** 用户批准后直接执行对应步骤，不重复询问；一次批准可覆盖已明确展示并获准的两项。只批准提交不等于批准打包，反之亦然。代码、文件范围或构建输入发生实质变化时，展示差异并重新 review；沉默和超时不算批准。
- **步骤互不阻塞。** 一项等待 review 或被关闭时，继续另一项已授权且条件具备的工作。例如 `git_commit=review wheel_build=auto` 可先从固定的未提交源码副本打包，不能为此擅自提交。

在进入可选步骤前简短说明本次生效的开关；无需为已经明确的模式再次确认。仅请求其中一项时，只读取对应说明：

- Git 提交：读 [references/git-commit.md](references/git-commit.md)。
- wheel 打包与产物验证：读 [references/wheel-build.md](references/wheel-build.md)。

## 先建立现场上下文

先读适用的 `AGENTS.md`，查看 `git status --short`、当前分支和提交，保留用户已有改动。定位仓库和相关入口后，优先从代码、日志及用户已提供的目录获取信息；只询问仍影响判断或执行的缺项。

建立简短的复现记录：

| 信息 | 需要明确的内容 |
| --- | --- |
| 机台 | 厂商、AVI/AOI/其他子型、线上/离线/手动等变体、资料格式版本 |
| 客户现象 | 预期与实际输出、错误日志、具体板号/板面/缺陷或图像编号、出现频率 |
| 迁回资料 | 检测包、参考图、Gerber/CAM、VRS/判定结果和相关配置的路径及对应关系；哪些是此分支必需的 |
| 运行条件 | 客户安装的 wheel/版本、Python、操作系统和架构、依赖及原生库环境、调用参数 |
| 验证基准 | 能复现问题的最小样本、同机台正常样本、客户认可的正确结果或可核验的业务规则 |

对实际参与复现的文件记录大小、必要的校验值和相对路径；完整大资料无需一开始全部扫描或哈希。保留迁回原件，需解包、写入或可视化时在副本或独立输出目录操作。客户资料、绝对路径、日志和大图不直接加入 Git；测试优先用合成或脱敏的最小样本。资料不全时继续完成可做的代码追踪，明确复现和验收尚缺什么。

## 阅读解析链路

按任务选择相关文件，不通读所有机台。

| 位置 | 用途 |
| --- | --- |
| `equapter/adapter/__init__.py` | `EquipmentType`、`RawDataParser`、`RawDataParserAOI`、`Buffer` 基础接口 |
| `equapter/adapter/comm/struct/__init__.py`、`raw_data.py` | 前者定义 `RawData`；后者定义 `SingleNGP`、`InfoNGP`、缺陷有效性标志和图像字段 |
| `equapter/adapter/comm/result_codes.py` | 状态码及错误描述，包含部分异常堆栈 |
| `equapter/equips/<厂商>/<类型>/parser.py`、`buffer.py` | 机台解析入口、工厂路由、参考资料缓存；部分实现另有文件名 |
| 对应厂商的 `utils/`、机台的 `comm/` 或 `common/` | 文件解包、图像解码、坐标、参考图及 Gerber 处理 |
| `equapter/adapter/comm/baseops/` | 公共坐标转换、图像裁剪对齐、缺陷合并与 `SplitterMerger` |
| `demo/<厂商>/<类型>/` | 调用示例；可能有历史路径、筛选条件和 GUI 阻塞，不等于自动化测试 |
| `equapter/version.py`、`equapter/equater.cfg`、机台 `__init__.py` | 发布版本组成；配置文件实际拼写是 `equater.cfg` |
| `setup.py`、`deploy.sh`、`clean_repo.py`、`requirements.txt` | 构建、依赖及发布行为，执行前必须阅读 |

从 demo 或客户调用处追踪到真实类和方法，说明：文件发现与配对 → 格式/版本识别 → 解包解码 → 元数据和坐标 → 参考图/Gerber/对齐 → 输出组织 → 调用方后续处理。标明每一步的关键输入、单位、配置、状态码和分支条件，并给出代码定位。

**不要假定全库返回值统一。** 常见 AVI 接口为 `(status, raw_data)`；AOI 常见四元组，`machvision/avif/raw_data_parser.py` 还有五元组实现。按实际返回语句和调用方核实。`status is not None` 也不等同于完全无数据，例如凯马部分失败会保留检测图；同时检查状态的 `code/level/description`、返回数据及缺陷有效性标志。

凯马 AVI 可从以下链路入手，其他机台重新确认：

```text
demo/kaima/avi/demo_raw_data_parser.py
  → equapter/equips/kaima/avi/parser.py: ParserFactory → RawDataAVIKM.parse
  → equapter/equips/kaima/utils/chk_pkg.py: KaiMaFactory → 对应检测包解析类
  → equapter/equips/kaima/utils/pkg_unpacker.py: UtilityUnpacker
  → RefImageBuffer / GbrImageBuffer / AlignImageBuffer、VrsPackParser
  → avi/comm/image_tuplet.py: ChkRefGbrTuplet → RawData
  → 调用方按需执行 SplitterMerger
```

## 用迁回资料定位和修复

1. **建立可信复现。** 先确认解释器、依赖版本，以及 `equapter.__file__` 和目标解析模块的 `__file__`，排除运行了已安装旧包或残留编译模块。依据现有 demo 提取最小入口，显式传入本次样本和配置；检查其中是否只处理某一板面或编号。无显示环境时保存必要的图像与数值，不直接运行 `imshow/waitKey`。
2. **固定输入和基线。** 用同一份原始资料和配置记录修复前的状态、缺陷/图像数量、尺寸、坐标及问题截图或数组摘要。核实 demo 传的是整份 JSON 还是 `Base_config`。凯马解析可能写入 `config_post`，缓存主要按路径和板面命中；每次对照实验重新读取/深拷贝配置并新建 parser/buffer。缓存相关问题另外保留复用实例的调用顺序复现。
3. **找到最早偏离预期的阶段。** 比较文件枚举、包头版本、解包长度、图像通道、元数据、坐标变换和输出配对。针对现象逐层缩小范围：缺图检查长度/偏移/解码/板面/IR；错位检查单位、精度、原点、翻转、缩放、裁剪和对齐；漏点检查过滤阈值、无效标志、索引配对及拆分合并。明确 `(x, y)` 与数组 `[y, x]`、宽高顺序、全板与局部坐标，以及 bbox 边界约定。
4. **用证据区分原因。** 区分资料损坏/缺失、配置或环境不匹配、尚未支持的格式和代码逻辑错误。关联“原始字段/图像 → 条件或计算 → 错误输出”。遇到宽泛异常捕获时检查状态中的堆栈，必要时在临时调试入口直接调用下层函数；不靠吞异常、返回成功或丢弃缺陷掩盖问题。
5. **实施范围合适的修复。** 在负责该行为的层级修改，保留既有调用签名、默认行为、输出顺序、状态和缺陷字段语义。格式差异用可验证的版本/结构判断，不硬编码客户名、板号或本地目录。若改公共逻辑，搜索实际调用者并评估受影响机台；临时日志、图像写出和断点在交付前清理。
6. **验证业务结果。** 保留能在旧实现暴露问题、在新实现通过的最小回归。至少复测故障样本和相关正常样本，按变更覆盖必要的板面、IR、空缺陷、格式版本或异常输入边界；公共代码再覆盖有相同调用路径的机台。比对点位、图像配对、坐标与状态等实际行为，不能只确认“没有异常”。测试目录或框架未建立时，使用可重复执行的断言脚本；不要把交互 demo 当成通过的测试。

给出根因与验证结论时，分别标注已证实、推测和未覆盖项。缺依赖或客户样本时不能宣称现场问题已解决，仍可完成可独立验证的单元逻辑及修复准备。

## 开发新机台解析方法

先从代表性正常/异常资料整理最小格式说明：文件配套关系、包头/版本、编码与字节序、图像排列、坐标单位、板面、缺陷标识及必要配置。没有依据的字段含义保持待确认，不从单个样本猜成全局规则。

选择输入格式和输出需求最接近的现有解析器，确认哪些公共能力可复用、哪些是原机台专用行为。先完成一个样本从原始包到目标输出的闭环，再扩展必要变体。依据现有调用方式补齐解析器、必要缓存/工具、工厂或枚举路由、可重复 demo 和回归；新增枚举先检查值与路由，避免意外别名。仓库忽略 `demo/` 下未跟踪的文件，新增示例或回归应选择可跟踪位置；只有请求提交时才按 Git 开关将其纳入提交。不要为新增机台顺便统一所有旧接口。

交付时说明支持的格式/版本、必需与可选文件、配置、返回契约及暂不支持的情况，并验证选定的旧机台路径没有回归。

## 汇报与后续积累

根据实际任务交付：解析链路及代码定位，或问题复现/根因/修复范围/回归结果。分别汇报 Git 与 wheel 的状态（未请求、关闭、待 review、已完成或受阻），已完成时附提交哈希或 wheel 及其源码快照信息。清楚说明哪些因资料或环境受限仍待验证，避免要求用户重新阅读过程消息。

将后续确认的机台格式规律和可复用排障经验逐步沉淀到本 skill；只有内容足够独立且反复使用时才拆为 `references/` 或增加 `scripts/`，并从此文件说明何时使用。不把单次客户路径、未验证猜测或临时绕过写成永久规则。

调用示例：

- `$equapter-maintenance 解释凯马 AVI 这份迁回资料如何解析，列出配置、文件配对关系和调用链，暂不改代码。`
- `$equapter-maintenance git_commit=review wheel_build=review 客户反馈下板 IR 图像缺失，请用指定资料复现、修复并回归，提交和打包分别等我 review 后执行。`
- `$equapter-maintenance git_commit=auto wheel_build=auto 请全自动修复、回归、提交并打包，客户环境为……。`
- `$equapter-maintenance git_commit=auto wheel_build=review 修复后自动提交，打包前给我看具体方案。`
- `$equapter-maintenance git_commit=off wheel_build=auto 不提交，用这次修复后的固定源码副本打包，并记录未提交差异。`
- `$equapter-maintenance 根据这组样本新增指定机台解析支持，沿用合适的现有输出接口，补充 demo 和回归。`
